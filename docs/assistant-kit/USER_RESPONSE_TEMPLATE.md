# YTM Importer — еталон відповіді користувачу

**Обов'язково читати перед кожною відповіддю про виконання роботи, збірку APK або PHONE QA.**
Цей стабільний формат схвалений власником проєкту 2026-10-08. Застосовувати і після
зміни чату/моделі, і після перерви. Поточні SHA, run та наступну дію брати з
`RESUME_HERE.md` + актуального GitHub, а не копіювати з прикладу.

## ОБОВ'ЯЗКОВИЙ СИГНАЛ: ручна дія користувача (2026-10-10)

**Це правило має пріоритет над звичайним порядком «шапка → результат → Termux в кінці».**
Коли робота ЗАРАЗ заблокована дією власника (насамперед ручним запуском
підписаного APK), **починай відповідь** із одного помітного попередження —
не ховай інструкцію в довгому звіті:

🟨 **ПОТРІБНА ДІЯ — ЗАПУСТИ APK ВРУЧНУ**

**Що натиснути:** [одне точне посилання на GitHub Actions або шлях через
Termux:Widget] → [назва кнопки/пункт меню] → [потрібна гілка].
**Звір:** `HEAD: 12345678` (лише приклад; завжди отримати актуальні 8 символів із GitHub).

- Якщо клієнт підтримує кольорові попереджувальні позначки, показуй один
  **жовтий/warning badge** «ПОТРІБНА ДІЯ» поруч із жирним «ЗАПУСТИ APK ВРУЧНУ».
  Якщо не підтримує — залишай видиме `🟨` та жирний текст.
- Виділяй **лише одну реально необхідну наступну дію**: одне посилання,
  одна правильна гілка, одна коротка інструкція; не починай із історії CI.
- Перед вимогою ручної дії перевір, що її не можна виконати своїми
  доступними інструментами; якщо можна — виконай сам. Не проси запускати
  APK до Validate PASS поточного HEAD.
- Якщо signed APK уже готовий для того самого HEAD — запропонуй
  **завантажити**, а не знову запускати збірку.
- Якщо користувачеві нічого не потрібно натискати, скажи коротко
  **«Твоїх дій не потрібно»** і продовжуй доступну роботу.
- Не обіцяй «сам перевірю пізніше» без насправді налаштованого
  моніторингу; чітко відрізняй Validate PASS, signed APK і PHONE PASS.

## Порядок відповіді — без перестановок## Режим виконання завдань — підтверджено власником 2026-10-09

**Не зупинятися між етапами звичайної роботи за командою «продовжуй».** Користувач формулює завдання один раз. Асистент самостійно отримує актуальний GitHub-стан, аналізує й змінює код, запускає доступні перевірки та CI, розбирає логи, виправляє знайдені помилки й повторює перевірку до конкретного перевіреного результату або реального блокера. Статуси не замінюють виконання. Для тривалої роботи три видимі частини — лише контроль прогресу, **не запит дозволу**.

**Звертатися до користувача тільки з конкретною необхідною дією** (телефон/Termux, автентифікація, недоступні файли або секрети, погодження ризикованої операції чи запису в YTM); називати точний пункт меню та очікуваний результат. Не просити користувача тестувати те, що можна автоматично перевірити, не повторювати вже прийнятий PHONE QA. Якщо роботу можна виконувати далі власними інструментами, продовжувати без очікування відповіді. Поза активним повідомленням немає самостійного фонового виконання; не обіцяти його.

Повний пріоритетний контракт: `YTM_ASSISTANT_WORKFLOW.md → §0 AUTONOMOUS TASK LOOP`.



**1. Шапка — 1–2 короткі речення.** Формат:
**«YTM Importer #NN — виправляємо [назва конкретного дефекту]».**
Відразу скажи, що виправляється/зараз перевіряється. Не починай з довгої
хронології, технічного звіту чи переліку Actions.

**2. Основна частина — стисле корисне пояснення.**
Що конкретно зроблено, що змінилося для користувача, а також чесний
статус `код готовий / Validate PASS / signed APK готовий / PHONE PASS`.
Додай commit/run тільки якщо вони дійсно підтверджені й допомагають.
Поясни важливі ризики/блокери, але не переповідай усі попередні кроки.
Закриті #29/#30/#40 та вже прийняті #58 тести не повторюй.
Готові тестові URL/тексти/команди надавай **одразу**, коли вони потрібні.

**3. В КІНЦІ — короткий `Termux` блок**, користувацькі номери та назви:
- Якщо точний поточний HEAD вже пройшов Validate, але signed APK немає:
  `Termux:Widget → YTM Importer → 1 — Оновити проєкт → 5 — Зібрати новий APK`;
  після успішної підписаної збірки `3 — Завантажити готовий APK → 4 — Відкрити папку з APK` (встановити).
- Якщо signed APK **для точно цього HEAD** уже готовий, не запускати нову
  збірку: `1 — Оновити проєкт → 3 — Завантажити готовий APK → 4 — Відкрити папку з APK`.
- Якщо Validate ще йде або не пройшов: **«Termux: поки нічого; очікуємо/виправляємо Validate»**.
  Ніколи не відправляй користувача у збірку неперевіреного HEAD.
- Якщо зараз жодних дій на телефоні немає: **«Termux: нічого не потрібно»**.
- Меню та нумерацію звіряй із `TERMUX_COMMANDS.md` / `tools/termux/`.
  Ніяких сирих `git`/`gh` команд, якщо меню вже має потрібну дію.

**4. ОСТАННІЙ абзац — `Тест після APK`, максимум 1–3 короткі дії:**
- Писати лише при реальній потребі встановити новий APK, і тільки нову
  змінену поведінку; вказати точний шлях у UI та очікуваний результат.
- Запитувати компактну відповідь `+` / `−`, скриншот лише при проблемі.
- Якщо APK не потрібен: **«Тест після APK: зараз не потрібен»**.
- Не перезапускати вже прийняту PHONE-матрицю без зміни її власника або
  нових суперечливих доказів. Не називати CODE/CI PASS як PHONE PASS.

## Довга робота в YTM Importer

Якщо завдання тривале/складне, зберігати **рівно три видимі частини**:
`Частина 1/3`, `Частина 2/3`, `Частина 3/3`, кожна з коротким
`виконана` після фактичного завершення. Не дублювати весь звіт після
кожної перевірки статусу. Проміжні повідомлення короткі, по суті.
Тільки у фінальній завершальній відповіді внизу містяться **Termux і тест**.

## Приклад фінальної відповіді (лише ФОРМАТ — не поточний CI-статус)

**YTM Importer #58 — виправляємо прокручування Review в альбомній орієнтації.**

Перенесено шапку й фільтри всередину прокручуваного списку.
Кнопка «Далі → Створити / додати» залишається внизу.
Validate PASS; PHONE ще не перевірено.

**Termux:** 1 — Оновити проєкт → 5 — Зібрати новий APK;
після успішної збірки 3 — Завантажити готовий APK → 4 — Відкрити папку з APK.

**Тест після APK:** відкрити «Перевірка треків», повернути горизонтально,
прокрутити до ручного Mezziah, натиснути й перевірити, що відкрився саме
цей трек. Відповідь: `+` або `−`.

**Правило:** якщо реальний signed APK чи Validate ще не готові, замінити
приклад на чесний поточний статус та не пропонувати передчасну збірку.
