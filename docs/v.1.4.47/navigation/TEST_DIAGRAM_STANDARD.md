# YTM Importer — стандарт тестових діаграм

Цей документ є обов'язковим контрактом для майбутніх phone-QA діаграм.

## 1. Повний маршрут

Кожна тестова діаграма **завжди починається з `[Головна]`**.

Порядок:
1. `[Головна]`;
2. конкретний блок головної сторінки;
3. конкретний об'єкт/кнопка блока;
4. кожний наступний екран, вікно або системний крок;
5. ціль тесту;
6. фінальний результат `PASS` / `FAIL`.

Локальні фрагменти, що починаються одразу з внутрішнього екрана або progress-вікна, не є повною тестовою діаграмою.

## 2. Об'єкти на кожному кроці

Для КОЖНОГО кроку маршруту окремими гілками показуються всі релевантні об'єкти:
- кнопки;
- поля вводу;
- фільтри;
- інформаційні блоки;
- Help windows / довідкові вікна;
- вікна підтвердження;
- progress/status вікна;
- result/error вікна;
- `←`;
- Android system Back;
- `Скасувати`;
- `Закрити`;
- дії підтвердження;
- rotation / recreation, якщо це частина тесту.

## 3. Стани

На кожному кроці показуються всі стани, які можуть змінити поведінку або вигляд:
- loading / завантаження;
- empty / порожньо;
- enabled / disabled;
- pending / очікує;
- active / виконується;
- added / додано;
- duplicate / дублікат;
- failed / помилка;
- completed / завершено;
- authorization / quota стани, якщо вони належать маршруту.

Стани запису в YTM у UI позначаються насамперед українською:
- `… Очікує`;
- `● Додаю…`;
- `✓ Додано`;
- `≋ Дублікат • пропущено`;
- `× Помилка`.

## 4. Мова

Первинна мова діаграм — **українська**.

Назви екранів, кнопок, полів і вікон мають повторювати фактичний український UI застосунку.

Англійська термінологія дозволена тільки:
- як вторинне уточнення в дужках;
- або якщо англійський термін уже присутній у самому UI.

Приклад: `кеш (cache)`, а не `cache` як основний підпис.

## 5. Джерело істини

Маршрути не вгадуються.

Перед побудовою діаграми маршрут і всі доступні дії перевіряються за актуальним source code тієї самої commit-версії, яку тестує APK.

Phone-QA є остаточним підтвердженням фактичної поведінки.

## 6. Власник маршруту

Однаковий внутрішній екран може бути відкритий з різних точок входу. Ці маршрути **не об'єднуються**, якщо Back/Cancel повинен повертати до різних батьків.

Приклади:
- `[Головна] → 4 кроки до плейлиста → 3. Знайти / перевірити → [Перевірка треків]`
  має власника `Головна`; Back повертає на `[Головна]`.
- `[Головна] → Поточний плейлист → [Поточний плейлист] → Знайти / перевірити → [Перевірка треків]`
  має власника `Поточний плейлист`; Back повертає в `[Поточний плейлист]`.
- `[Головна] → нижня панель → Плейлист → [Поточний плейлист] → ...`
  також тестується як окрема точка входу, навіть якщо використовує той самий `PlaylistActivity`.

Діаграма завжди показує не тільки `куди зайшли`, а й `кому належить Back`.

## 7. Пакети тестів

Phone-QA подається користувачу максимум по **3 тести за один пакет**.

Кожний тест має власну повну діаграму.

## 8. MOBILE / DESKTOP структура

Рекомендована структура:

```text
<test-package>/
├── index.html
├── README.md
├── mobile/
│   ├── TEST_01.svg
│   └── TEST_01.png
└── desktop/
    ├── TEST_01.svg
    └── TEST_01.png
```

- `index.html` знаходиться на рівень вище `mobile/` і `desktop/`;
- MOBILE: зверху вниз, орієнтація під телефон;
- DESKTOP: зліва направо, орієнтація під ПК;
- логіка, ID вузлів, стани й підписи в обох варіантах однакові; змінюється тільки layout.

## 9. Візуальні типи вузлів

Рекомендована семантика:
- `[Екран]` — екран / Activity;
- `{Вікно}` — modal / confirm / result;
- `{Help}` — інформаційне або довідкове вікно;
- `[/ Поле /]` — поле вводу / пошуку / вибору;
- `Стан:` — runtime state;
- `PASS` / `FAIL` — кінцева перевірка.

Основний тестовий шлях виділяється сильніше; альтернативні можливості — боковими гілками.

## 10. Phone-QA звіт

Користувач може відповідати коротко:
`1+`, `2-`, `3+`.

Якщо FAIL стосується конкретного вузла, він описується через шлях/стан, наприклад:
`WRITE.TRACK.ADDED → FAIL: UI залишився «… Очікує»`.

Це дозволяє прив'язати finding до конкретного transition/state у source code.
