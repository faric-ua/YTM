# v1.4.30 — NEW / UPDATED / MISSING, QA R1

Статус: **PHONE QA NOT RUN**. Пакет додає інструкції та локальний валідатор.
База: `faric-ua/YTM`, commit `c50e331a892e75eec6ffcb0b1808678729c9d392`,
Android `versionName=1.4.30`, `versionCode=64`.

Попередній closeout SELECTED(2) + UNCHANGED залишається чинним. Цей run перевіряє
нові сценарії окремо. Він не означає повну регресію застосунку.

## Чому новий ALL baseline

У SELECTED baseline зафіксовані playlist IDs. Створений пізніше плейлист має новий ID,
тому не потрапляє в цей scope. Для справжнього NEW створюємо свіжий **ALL export B0**,
і лише після його перевірки створюємо один власний приватний QA-плейлист.
Не редагуємо `scopePlaylistIds`, fingerprints, лічильники або manifest вручну.

Ізольований run лежить у `Download/YTM-v1.4.30-Delta-QA-R1/`:

| Папка | Що зберігаємо |
|---|---|
| `sources/` | B0, D1, D2, D3 — прямі дочірні папки, створені застосунком |
| `restored/` | F1, F2, F3 — окремі consolidated результати |
| `reports/` | Короткі результати локальної перевірки |
| `run.json` | Назва/ID тестового плейлиста, прийняті сесії та SHA-256 snapshots |

Позначення B0/D1/F1 — лише пояснення: **не перейменовувати фактичні папки**.
`baseSessionName` посилається на точну назву попередньої сесії.
Наступний incremental запускаємо від попереднього **delta**, а не від F1/F2.
Consolidated результати тримаємо окремо від джерел, щоб не змішати chain heads.

## Контрольні дані

Валідатор після B0 визначить N = кількість записів, E = непорожні projects,
K = SKIPPED_EMPTY. Завжди N = E + K; жодного припущення про 2 або 21 плейлист.

`prepare` надрукує унікальну назву `YTM-QA-1430-<UTC date/time>-TEST`.
Створюємо лише цей новий власний приватний плейлист. Не перейменовуємо під нього
старий `YTM QA Existing Target` та не змінюємо `top 3`.

Для A і B вибираємо два різні доступні треки з уже знайомого `top 3` або іншого
власного плейлиста. Додаємо їх до QA-плейлиста через YouTube/YouTube Music:
спочатку A, потім B. Це мають бути ті самі конкретні відео, а не інші версії пісень.
Валідатор зафіксує точні video IDs із D1. Додавати третій трек не потрібно.

Для UPDATED змінюємо **лише ручний порядок A,B → B,A**. Назва, privacy, ID і
кількість 2 лишаються такими самими. Так ми перевіримо fingerprint і replacement
навіть за незмінної кількості треків. Потрібно зберегти саме порядок плейлиста,
а не лише вибрати локальне сортування у перегляді YouTube Music.

Для MISSING видаляємо через YouTube/YouTube Music **тільки цей QA-плейлист**,
створений у поточному run. Перед видаленням звіряємо назву та ID з `status`.
Видалення з онлайн-акаунта остаточне для цього disposable тесту; локальні D1/D2/F1/F2
зберігають його стани. Скрипт нічого не створює, не змінює та не видаляє в акаунті.
Самого приховування плейлиста з екрана бібліотеки може бути недостатньо для MISSING.

Під час run інші плейлисти не змінюємо. Якщо вони змінилися самі або іншою програмою,
очікувані значення вже не відповідають контрольному сценарію: зберігаємо результат,
надсилаємо preview, з'ясовуємо відхилення. Це не автоматичний FAIL застосунку.

## Очікувані значення

| Етап | Baseline для incremental | NEW | UPDATED | UNCHANGED | MISSING | FAILED | Нові project-файли у delta |
|---|---|---:|---:|---:|---:|---:|---:|
| D1: додали A,B | B0 | 1 | 0 | N | 0 | 0 | 1 |
| D2: порядок B,A | D1 | 0 | 1 | N | 0 | 0 | 1 |
| D3: видалили QA-плейлист | D2 | 0 | 0 | N | 1 | 0 | 0 |

| Результат | Довжина chain | playlistCount у delta | currentPlaylistCount у delta | playlistCount у full | Projects у full | Empty у full | QA-плейлист |
|---|---:|---:|---:|---:|---:|---:|---|
| F1 після D1 | 2 | N+1 | N+1 | N+1 | E+1 | K | A,B |
| F2 після D2 | 3 | N+1 | N+1 | N+1 | E+1 | K | B,A |
| F3 після D3 | 4 | N+1 | N | N | E | K | відсутній |

D3 містить запис MISSING, тому його `playlistCount` залишається N+1.
Consolidated F3 вже не має цього запису, тому його `playlistCount` дорівнює N.
Empty baseline записи враховуються, але окремих project-файлів для них немає.

## Етап 0 — підготувати run і baseline

Перший Termux блок від асистента перевірить/накладе пакет, виконає selftests та
`prepare`. Надіслати його результат. Новий APK для цього QA-пакета не потрібен.

Після перевірки результату асистентом:

1. У встановленому v1.4.30 відкрити `1. Імпорт`.
2. Натиснути `Експортувати всі плейлисти в папку`.
3. Вибрати `Download/YTM-v1.4.30-Delta-QA-R1/sources` як батьківську папку.
4. Дочекатися повного завершення. Зберегти скрін result dialog: ALL, exported,
   skipped, failed, requests. QA-плейлиста на цьому кроці ще немає.
5. Запустити:

```bash
ytm
python3 -B scripts/v1430-delta-status-qa.py baseline
```

Очікуємо `BASELINE FILE CHECK PASSED`, N/E/K та `phoneUI: PENDING_REVIEW`.
Надіслати вивід і скрін. Лише після перевірки переходити до NEW.
Baseline має бути свіжим schema 2 ALL export цієї встановленої версії, без FAILED.

## Етап 1 — NEW → F1

1. Створити названий тестовий приватний плейлист A,B. Перевірити онлайн, що два
   треки збережені. Інші плейлисти не змінювати.
2. `1. Імпорт` → `Оновити backup (incremental)` → вибрати B0 у `sources/`.
3. Preflight: ALL; оцінка `playlistItems.list`; `search.list: 0`; `write API: 0`.
4. `Перевірити зміни`: NEW=1, UPDATED=0, UNCHANGED=N, MISSING=0, FAILED=0.
   Зберегти скрін. Якщо інші значення — зупинитися тут і надіслати preview.
5. `Зберегти delta` → батьківська `sources/`. Отримаємо D1; не перейменовувати.
6. Виконати процедуру consolidated нижче з head D1, отримати F1 у `restored/`.
7. Відкрити F1 через `Відкрити backup / manifest.json`, знайти тестовий плейлист,
   відкрити його: два exact/ready треки в порядку A,B, проблемних 0.
8. У Review натиснути `Пошук`: потрібні треки 0, нові `search.list` 0.
   Зберегти скрін; не запускати пошук, якщо значення більше 0.
9. Запустити:

```bash
ytm
python3 -B scripts/v1430-delta-status-qa.py check new
```

Очікуємо `NEW DELTA + CONSOLIDATED FILE CHECK PASSED`.
Надіслати вивід і скріни, після перевірки перейти до UPDATED.

## Етап 2 — UPDATED → F2

1. У тому самому онлайн QA-плейлисті зберегти ручний порядок B,A.
   Не змінювати назву, privacy, кількість, відео чи ID плейлиста.
2. Incremental baseline = **D1**. Preflight ALL. Scan: UPDATED=1, UNCHANGED=N,
   решта 0. Зберегти скрін; delta D2 записати в `sources/`.
3. Consolidated з head D2: chain length 3, фінальних плейлистів N+1,
   джерел E+1, empty K, MISSING подій 0. Результат F2 у `restored/`.
4. Відкрити саме F2 через manifest-каталог. Тестовий плейлист має два треки B,A:
   старий A,B не залишився, додаткових копій немає. Review: exact/ready 2,
   problems 0, потрібний пошук 0, нові `search.list` 0. Зберегти скріни.
5. Запустити:

```bash
ytm
python3 -B scripts/v1430-delta-status-qa.py check updated
```

Очікуємо `UPDATED DELTA + CONSOLIDATED FILE CHECK PASSED`.
Надіслати вивід і скріни. До MISSING перейти лише після перевірки цього етапу.

## Етап 3 — MISSING → F3

Спочатку показати точний поточний тестовий target:


1. Звірити `targetTitle` / `targetId` з онлайн QA-плейлистом.
2. Видалити тільки цей створений для run плейлист через YouTube/YouTube Music.
   Не видаляти baseline, source delta, F1/F2 або інші онлайн плейлисти.
3. Incremental baseline = **D2**. ALL. Scan: MISSING=1, UNCHANGED=N,
   решта 0. Зберегти скрін; D3 записати в `sources/`. У ньому лише manifest.
4. Consolidated з head D3: chain length 4, фінальних плейлистів N, джерел E,

5. Відкрити саме F3 через manifest-каталог. QA-плейлист відсутній.
   Один незмінений baseline плейлист (наприклад `top 3`, якщо він був у B0)

6. Запустити:

```bash
ytm
python3 -B scripts/v1430-delta-status-qa.py check missing
```

Очікуємо `MISSING DELTA + CONSOLIDATED FILE CHECK PASSED`.
Це завершує локальне порівняння файлів. Підсумковий PHONE PASS визначає асистент
після перегляду всіх трьох наборів UI-доказів.

## Однакова процедура consolidated після кожної delta

1. `1. Імпорт` → `Зібрати повний backup з chain`.
2. Вибрати **спільну батьківську `sources/`**, не окрему D-папку.
3. Якщо є picker, вибрати найновішу delta поточного етапу D1/D2/D3.
   За єдиного head picker може бути пропущений автоматично.
4. Звірити Base B0, потрібний Head, ALL, довжину chain 2/3/4 і кількості з таблиці.
   `YouTube API = 0`. Зробити скрін preview.
5. Натиснути `Створити`, вибрати **`restored/`** як батьківську папку.
6. Дочекатися result dialog і зробити скрін. Нова папка має коротку назву
   `YYMMDD-HHMMSS-YTM-Full`. Кожен етап створює новий результат.

Backup scan виконує читання YouTube API для ALL scope; враховувати показану оцінку
запитів. `search.list=0` і `write API=0` стосуються операцій backup у застосунку.
Створення, перестановка та видалення тестового плейлиста окремо змінюють онлайн-акаунт.
Consolidated та Python-перевірка працюють локально. Нуль у manifest сам по собі
не доводить відсутність мережевих викликів: потрібні також UI-докази та перевірений код.

## Що доводить валідатор

- Версія/формат/scope, лічильники, статуси кожного ID, відсутність FAILED та error.
- B0 → D1 → D2 → D3, точні `baseSessionName`, Base/Head/sourceSessions у full.
- NEW — новий ID з потрібною назвою, private, два різні exact video IDs.
- UPDATED — той самий плейлист із точним порядком B,A за незмінного розміру.
- MISSING — запис у D3 є; у full F3 його немає. Старі звичайні та empty записи збережені.
- Усі очікувані projects, sourcePlaylistId, privacy, назви та впорядковані track-поля,
  а не лише загальна кількість файлів. Consolidated не зобов'язаний мати fingerprints:
  вони обчислюються з project-даних для звірки delta.
- SHA-256 раніше прийнятих джерел і результатів не змінилися між етапами.

Валідатор читає джерела та full outputs, записує тільки свій `run.json` і `reports/`.
Він не відновлює backup замість Android, не викликає API, не керує Google-акаунтом,
не доводить вигляд UI чи поведінку натискань. `OFFLINE_EVIDENCE_PASS` та
`phoneUI: PENDING_REVIEW` навмисно розділяють ці два види доказів.

## Якщо STOP або повторний запуск

Зберегти вивід і фактичні папки. Не правити manifest, не підганяти counts/ID,
не видаляти попередні результати. Повторна перевірка прийнятого етапу — SKIP
із перевіркою збережених джерел. Повторне `prepare` не скидає run.

Скрипт очікує рівно одну нову delta й один новий full на етап. Незавершений export,
зайвий повторний result, кілька нових delta або зміна іншого плейлиста дають STOP,
щоб асистент міг зіставити реальний стан. Новий run за потреби використовує іншу
папку через `--run /sdcard/Download/<нова-папка>` у всіх командах. Старий run зберігаємо.

## Докази та closeout

Кожен етап: scan preview, chain preview, materialize result, normal-open каталог/треки,
для NEW/UPDATED — exact/search preview, плюс короткий console report.
Шаблон: `PHONE_TEST_RUN.md` у цій папці.

Перед передаванням скрінів прибрати email, аватар та приватні назви інших плейлистів.
Повні account backup, `run.json` і `.ytm-project.json` не додавати в Git і не надсилати
без потреби: вони містять бібліотеку акаунта. Короткий report достатній для першого review.

Після аналізу доказів асистент готує окремий closeout: фактичні PASS/FAIL/NOT RUN,
оновлення cumulative QA/status/commands/tutorial і точний блок stage/commit/push.
Цей пакет не переписує попередній v1.4.30 closeout і не позначає майбутні тести PASS.
